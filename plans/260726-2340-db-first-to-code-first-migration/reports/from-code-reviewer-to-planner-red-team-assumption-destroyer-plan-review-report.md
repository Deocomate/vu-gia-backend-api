# Red-Team Review: DB-first to Code-first Migration Plan

Role: Assumption Destroyer / Contract Verifier. All findings verified against the live source tree, not the plan's own claims.

## Finding 1: Dev-mode reset scope ignores 8 non-seeded tables that hold references into the 13 seeded tables
- **Severity:** Critical
- **Location:** Phase 2, section "Reset order" and "Architecture" (`SeedRunner`)
- **Flaw:** The reset list (phase-02-java-seeder-framework-and-data-port.md:64-70) only tears down the 12 seeded-domain repositories (coupon → page → faq → gallery → showroom → banner → news → newsCategory → product → productCategory → user → shippingMethod). It never touches `orders`, `order_items`, `cart_items`, `payment_transactions`, `refresh_tokens`, or `contact_requests` — 6 of the 21 tables (`redirects`/`newsletter_subscribers` are the other 2 non-seeded, no FK exposure) that carry `user_id`, `product_id`, `coupon_id`, `shipping_method_id`, `handled_by_id` columns pointing at the very rows being wiped.
- **Failure scenario:** A developer runs `APP_ENV=development`, logs in (creates `refresh_tokens` row), adds a product to cart (`cart_items.user_id`/`product_id`), places a test order (`orders.user_id/coupon_id/shipping_method_id`, `order_items.product_id`). On the next restart, `userSeeder.reset()`/`productSeeder.reset()`/`couponSeeder.reset()`/`shippingMethodSeeder.reset()` delete and reinsert those parent rows with new IDs, but the leftover `orders`/`cart_items`/`order_items`/`refresh_tokens` rows still reference the old (now-gone or reassigned) IDs. Because `V1__init_db.sql` declares **zero real `FOREIGN KEY` constraints** (verified: `grep -i "FOREIGN\|CONSTRAINT" V1__init_db.sql` → only `SET FOREIGN_KEY_CHECKS`), MySQL will not reject this — it silently leaves dangling/misattributed references. Any subsequent `GET /orders/{id}` or refresh-token validation that lazy-loads the referenced `UserEntity`/`ProductEntity` will hit `EntityNotFoundException` or, worse, silently resolve to a *different* re-seeded entity that now occupies a nearby ID.
- **Evidence:** `src/main/resources/db/migration/V1__init_db.sql` — no `FOREIGN KEY`/`CONSTRAINT` anywhere (lines 1-412, only `FOREIGN_KEY_CHECKS` pragma at lines 6/413); `orders` table columns `user_id`, `coupon_id`, `shipping_method_id` (V1 lines 220,233,236) and `cart_items.user_id/product_id` (V1 lines 180-181) have no FK constraint to catch this. Plan's own framing ("DB treated as disposable", plan.md:19) implies the *whole* dev DB should be safely resettable, but the implementation only resets 13 of 21 tables.
- **Suggested fix:** Either (a) extend dev-mode reset to also truncate `orders`, `order_items`, `cart_items`, `payment_transactions`, `refresh_tokens`, `contact_requests` before reseeding, or (b) explicitly document in the plan that dev-mode reset is scoped to reference/catalog data only and that transactional dev data will orphan on every restart — and decide whether that's acceptable. Currently neither the plan nor its acceptance criteria mention this at all.

## Finding 2: UserSeeder spec hardcodes `role=SUPERADMIN`; actual seed data is `role='ADMIN'` — privilege escalation
- **Severity:** Critical
- **Location:** Phase 2, section "Architecture" → `UserSeeder` paragraph (phase-02:62)
- **Flaw:** The plan states: *"UserSeeder: seeds exactly the one admin row from V2__seed_db.sql (admin / admin@gomvugia.vn / admin123, ... role=SUPERADMIN)."* The actual source row in `V2__seed_db.sql` sets `role` to `'ADMIN'`, not `'SUPERADMIN'`.
- **Failure scenario:** `UserController` gates account creation (`POST /users`) and role promotion/demotion (`PATCH /users/{id}/role`) with `@PreAuthorize("hasRole('SUPERADMIN')")` — strictly higher privilege than `ADMIN` (which cannot create accounts or change roles, only `hasAnyRole('ADMIN','SUPERADMIN')` reads/searches/password-resets-for-customers-only). If Phase 2 is implemented exactly as written, the canonical `admin@gomvugia.vn` account gains the ability to create new admin accounts and reassign any user's role — capabilities it does not have today. This directly contradicts the plan's own decision ("port 1:1, no reduced/curated dataset", plan.md:24) and the acceptance criterion "no data correctness regression" (plan.md:49).
- **Evidence:** `src/main/resources/db/seed/V2__seed_db.sql:71` — `'ADMIN'` (row values: id=2, username='admin', role='ADMIN'). `src/main/java/vn/springboot/controller/UserController.java:49,56` — `@PreAuthorize("hasRole('SUPERADMIN')")` on `create()` and `changeRole()`.
- **Suggested fix:** Change the `UserSeeder` spec (and Phase 2 success criteria) to seed `role=ADMIN`, matching the source SQL exactly. If `SUPERADMIN` is actually desired going forward, that's a scope decision the user must explicitly make — not something to slip in silently during a "1:1 port."

## Finding 3: Reset via `deleteAllInBatch()`/`deleteAll()` (not `TRUNCATE`) does not reset MySQL AUTO_INCREMENT — breaks "byte-for-byte equivalent" claim
- **Severity:** High
- **Location:** Phase 2, section "Reset order" (phase-02:71) and plan.md Acceptance Criteria (plan.md:47)
- **Flaw:** Plan mandates: *"Use `repository.deleteAllInBatch()` (or `deleteAll()`...) — not raw SQL `TRUNCATE`, to stay consistent with the code-first, JPA-only approach."* All seeded entities extend `BaseEntity` with `@GeneratedValue(strategy = GenerationType.IDENTITY)` (MySQL `AUTO_INCREMENT`). Plain `DELETE` statements (which is what `deleteAllInBatch()`/`deleteAll()` issue) do **not** reset InnoDB's `AUTO_INCREMENT` counter in MySQL 8 — only `TRUNCATE` or an explicit `ALTER TABLE ... AUTO_INCREMENT = 1` does. The counter is also persisted in the redo log across restarts in MySQL 8.0+, so it survives container restarts too.
- **Failure scenario:** Today, `V2__seed_db.sql` starts with `TRUNCATE TABLE` for every seeded table (V2__seed_db.sql:15-39), guaranteeing product #1 is always id=1, category #1 is always id=1, etc., every time the dev DB is clean-reseeded via `FlywayDevCleanConfig`. Under the new Java seeder, dev-mode restart #1 seeds products as ids 1-12; restart #2 (same container, same volume) seeds them as ids 13-24; restart #3 as 25-36, and so on forever. This breaks plan.md's own acceptance criterion: *"data is byte-for-byte equivalent in structure/content to today's V2__seed_db.sql"* (ids are part of that content/structure) and breaks any hardcoded dev fixture, Postman collection, or manual QA bookmark (`GET /products/1`) that assumed stable low IDs — a real behavior regression versus the current TRUNCATE-based dev-clean flow.
- **Evidence:** `src/main/java/vn/springboot/common/entity/BaseEntity.java:28` — `@GeneratedValue(strategy = GenerationType.IDENTITY)`; `src/main/resources/db/seed/V2__seed_db.sql:15-39` — explicit `TRUNCATE TABLE` calls (which do reset AUTO_INCREMENT) precede every insert today.
- **Suggested fix:** Either accept and explicitly document the ID-drift behavior (updating the "byte-for-byte equivalent" acceptance criterion to exclude IDs), or reset the AUTO_INCREMENT counter per table after each `reset()` (e.g. native query `ALTER TABLE <table> AUTO_INCREMENT = 1`) if stable dev IDs matter.

## Finding 4: Docker/Actuator healthcheck can report "healthy" mid-seed — no readiness gate tied to seeding
- **Severity:** High
- **Location:** Phase 3, "Related Code Files" re: `docker-compose.yml` healthcheck (phase-03:29); not revisited in Phase 4
- **Flaw:** `SeedRunner` is specified as a `CommandLineRunner` (phase-02:24, "orchestrates all seeders per profile"). Spring Boot starts the embedded Tomcat server during `ApplicationContext.refresh()`, which completes *before* `CommandLineRunner` beans execute (`SpringApplication.callRunners()` runs after `refresh()` returns). `management.health` in `application.yaml` only disables the mail indicator (application.yaml:121-130) — it does not add any indicator gating on seed completion; the default `db` health indicator only does a `SELECT 1`-style connectivity check. This means `/actuator/health` (and thus `docker-compose.yml`'s `curl -fsS http://localhost:8080/actuator/health` healthcheck) can report `UP` while `SeedRunner` is still mid-`reset()` (dev mode, tables truncated) or mid-first-`seed()` (any profile, tables still empty).
- **Failure scenario:** On a fresh prod deploy (`APP_ENV` unset → idempotent seed-once path) or any dev restart, if the reverse proxy/orchestrator (Coolify/Traefik, per docker-compose.yml's own comments) starts routing traffic once Docker's healthcheck passes, a request landing in that window sees an empty product/news/coupon catalog, or (in dev) a half-wiped DB with only some of the 13 domains reset so far — a materially worse and less obvious failure mode than the SQL-batch approach the plan's own risk note (phase-03:29) worries about only from a "is 90s long enough" timing angle, not a correctness angle.
- **Evidence:** `src/main/resources/application.yaml:120-130` — no custom `HealthIndicator` tied to seeding; `docker-compose.yml:100-108` — healthcheck hits `/actuator/health` directly, `start_period: 90s`.
- **Suggested fix:** Either make `SeedRunner` block readiness (e.g. custom `HealthIndicator` that reports `DOWN` until all seeders report non-empty, wired into `management.endpoint.health.group.readiness`), or explicitly accept and document that traffic may briefly hit an unseeded instance on first boot.

## Finding 5: `ShippingMethodEntity.code` (`nullable=false`) has no DTO field or service wiring — admin "create shipping method" stays broken, contradicted by the plan's own risk note
- **Severity:** High
- **Location:** Phase 1, Implementation Step 1 (phase-01:34) vs. Risk Assessment (phase-01:53)
- **Flaw:** Step 1 unconditionally instructs: *"code (String, @Column(unique = true, length = 50, nullable = false))"*. The phase's own Risk Assessment explicitly warns: *"adding `unique = true` on `ShippingMethodEntity.code` ... could break current runtime if any code path already inserts shipping methods without a code ... grep for existing call sites before adding `nullable = false`"* — but no implementation step actually performs that conditional check, and no later phase closes the gap it identifies. `ShippingMethodServiceImpl.create()` builds the entity without ever setting `code` (no such field exists on `ShippingMethodCreateRequest`, and the mapper never maps it either).
- **Failure scenario:** After Phase 1, `POST /shipping-methods` (an existing, live admin endpoint) will fail every call — Hibernate raises `PropertyValueException` for a not-null field with no value before it even reaches the DB. This is a live regression to a currently-reachable admin API introduced by this migration and never remediated: neither Phase 1's nor Phase 2's Success Criteria mention updating `ShippingMethodCreateRequest`/`ShippingMethodUpdateRequest`/`ShippingMethodMapper` to accept/expose `code`.
- **Evidence:** `src/main/java/vn/springboot/service/impl/ShippingMethodServiceImpl.java:79-88` (`create()` never sets `.code(...)`); `src/main/java/vn/springboot/dto/request/shipping/ShippingMethodCreateRequest.java` (no `code` field); `src/main/java/vn/springboot/mapper/ShippingMethodMapper.java` (no `code` mapping).
- **Suggested fix:** Add `code` to `ShippingMethodCreateRequest`/`ShippingMethodUpdateRequest`, wire it through `ShippingMethodServiceImpl.create()`/`update()`, and add it to `ShippingMethodResponse`/mapper — as a required Phase 1 (or Phase 2) deliverable, not an afterthought risk note.

## Finding 6: Phase 2 claims JSON content exists for `detail_sections`/`functions`/`combo_gallery` that is never present in the actual seed SQL
- **Severity:** Medium
- **Location:** Phase 2, "Architecture" → `ProductSeeder` paragraph (phase-02:60)
- **Flaw:** The plan states: *"Simple JSON fields (description, detail_sections, functions, combo_gallery) can be Java text blocks transcribed literally from the SQL's JSON_OBJECT()/JSON_ARRAY() calls."* A full-text search of `V2__seed_db.sql` for these three column names returns **zero matches** — the `INSERT INTO products (...)` column list (V2__seed_db.sql:229-248) never even mentions `detail_sections`, `functions`, or `combo_gallery`; every product row (including the combo, id 12) leaves them at their implicit `NULL` default. The combo's actual "specifications"/"attributes" content lives nested inside the `description` JSON column instead (V2__seed_db.sql:627-636).
- **Failure scenario:** An implementer following the plan literally will look for source JSON to "transcribe" for these three fields, find nothing, and either (a) waste time hunting for non-existent content, or (b) fabricate placeholder JSON to "fill in" what the plan implies should exist — directly violating the project's no-fake-data rule and the plan's own "port 1:1 ... no reduced/curated dataset" decision (plan.md:24), since inventing content is the opposite of a faithful port.
- **Evidence:** `grep -n "detail_sections|functions|combo_gallery" V2__seed_db.sql` → no matches; `V2__seed_db.sql:229-248` (products INSERT column list omits all three).
- **Suggested fix:** Correct the plan text to state that `detail_sections`, `functions`, and `combo_gallery` are always `NULL` in the current seed data (leave them unset in `ProductSeeder`), and that combo sub-content lives inside `description`.

## Finding 7: No ID-resolution guidance for `product_category_id` in `ProductSeeder`, unlike the explicit treatment given to `news_category_id`
- **Severity:** Medium
- **Location:** Phase 2, Implementation Steps 4 vs. 5 (phase-02:78-79)
- **Flaw:** Step 5 explicitly instructs resolving `news_category_id` "via a small in-seeder map keyed by category name/slug, not hardcoded ids." Step 4 (`ProductSeeder`) gives no equivalent instruction for `product_category_id`, even though `products.product_category_id` in the source data is a literal FK to `product_categories.id` (1-6) with exactly the same generated-vs-literal-id mismatch risk as `news_category_id` (V2__seed_db.sql product rows reference category ids like `2`, `3` directly — e.g. line 276). Given Finding 3 (AUTO_INCREMENT no longer resets on dev reseed), category IDs are *not* guaranteed to stay 1-6 even on first boot if seeder execution order or retries change insertion count.
- **Failure scenario:** An implementer, seeing no explicit warning for this FK (unlike the one for news), hardcodes `product_category_id` literals matching the original SQL ids. This works by coincidence on a truly fresh DB where `ProductCategorySeeder` is the first-ever writer to that table, but silently produces wrong category assignments (or FK-referencing-nothing rows, since there's no DB FK constraint to catch it — see Finding 1) after any dev-mode restart once ids have drifted.
- **Evidence:** `phase-02:78` vs `phase-02:79`; `V2__seed_db.sql:276` (`product_category_id` = `2` as a literal in the products INSERT).
- **Suggested fix:** Apply the same category-lookup-by-slug/name pattern used for `NewsSeeder` to `ProductSeeder`'s `product_category_id` resolution, and call this out explicitly in Step 4 the way Step 5 does for news.

## Unresolved Questions
- Does the user want dev-mode reset to also cover transactional tables (`orders`, `cart_items`, etc.), or is the intent that only catalog/reference data resets and dev-created transactional data is expected to rot? Finding 1 needs an explicit product decision, not just a bug fix.
- Is `SUPERADMIN` actually the intended role for the canonical admin going forward, or should the 1:1 port literally carry over `ADMIN` as seeded today? Finding 2 needs the user to confirm before Phase 2 starts.
