# Red Team Review (Security Adversary) — DB-First to Code-First Migration Plan

Reviewer role: Security Adversary + Fact Checker. Scope: plan.md + phases 1-4.

## Finding 1: Seeded admin role escalated from ADMIN to SUPERADMIN, contradicting the plan's own "1:1 port" mandate

- **Severity:** Critical
- **Location:** Phase 2, section "Architecture" / `UserSeeder` description
- **Flaw:** Phase 2 line 62 states `UserSeeder` seeds the admin row with `role=SUPERADMIN`. The actual source data being ported — `V2__seed_db.sql` — seeds `role='ADMIN'`, not `SUPERADMIN`. `Role` is a 3-tier enum (`SUPERADMIN, ADMIN, CUSTOMER`) with real, distinct authorization consequences: `UserController.java:49,56` gate account creation and role promotion/demotion behind `@PreAuthorize("hasRole('SUPERADMIN')")` — ADMIN cannot create accounts or change any user's role; `resetPassword` (`UserController.java:64-65` comment) explicitly limits ADMIN to resetting CUSTOMER passwords only, while SUPERADMIN can reset anyone's. If the implementer follows Phase 2's literal spec (more actionable than the parent plan's abstract "port 1:1" principle in `plan.md:24`), the migration silently grants the seeded admin account a materially higher privilege tier than it has today — full user/role administration capability it never had — despite the plan's own acceptance criteria demanding no data/behavior drift from the SQL seed.
- **Failure scenario:** Post-migration, the `admin`/`admin123` credential set (already weak/well-known, see Finding 2) now grants SUPERADMIN powers: create arbitrary new SUPERADMIN/ADMIN accounts, promote any CUSTOMER to ADMIN/SUPERADMIN, and reset any admin's password — a strict privilege escalation over the pre-migration ADMIN-only account, introduced purely by a plan-authoring transcription error, not a deliberate decision recorded in "Confirmed decisions."
- **Evidence:** `V2__seed_db.sql:71` — `'ADMIN',` in the INSERT values for the users row; `plan.md:26` "Canonical admin account is `admin` / `admin@gomvugia.vn` / `admin123` (matches what's actually seeded today)" (i.e. plan asserts fidelity to the SQL seed) vs. `phase-02-java-seeder-framework-and-data-port.md:62` "role=SUPERADMIN"; `src/main/java/vn/springboot/controller/UserController.java:47-59` (`@PreAuthorize("hasRole('SUPERADMIN')")` on create/changeRole).
- **Suggested fix:** Seed `role=ADMIN` to match `V2__seed_db.sql` exactly, per the plan's own 1:1-port decision. If SUPERADMIN is actually desired (e.g. to replace `DataInitializer`'s SUPERADMIN default), that must be stated as an explicit "Confirmed decision" with the privilege change called out, not buried as an unstated architecture detail.

## Finding 2: Hardcoded admin password removes the only env-var override the current code has, and can auto-provision a well-known credential into a real production DB

- **Severity:** Critical
- **Location:** Phase 2, section "Architecture" / `UserSeeder`; Phase 3 (`ddl-auto=update` "everywhere (dev + prod)")
- **Flaw:** Current `DataInitializer.java:28-35` externalizes the seeded admin's username/email/password via `@Value("${app.init.admin-password:admin123}")` etc. — an operator can override the default password per-deployment via env var/application.yaml without touching code. Phase 2's `UserSeeder` replacement drops this entirely: "seeds exactly the one admin row from `V2__seed_db.sql` (`admin` / `admin@gomvugia.vn` / `admin123`, bcrypt-encoded via the existing `PasswordEncoder` bean...)" — no `@Value` override, credentials hardcoded in source. Combined with `plan.md:22` "`ddl-auto=update` everywhere (dev + prod)" and the non-dev seeding rule ("any other profile → seed only empty tables," `phase-02...md:19`), the very first boot against *any* genuinely empty database — including a real production DB on first deploy or after a disaster-recovery restore — auto-provisions a live, internet-reachable admin account with a password that is now permanently and publicly fixed in the git history/source tree.
- **Failure scenario:** First production deploy (or a redeployed/restored prod DB that happens to be empty) silently creates `admin`/`admin123` with no forced rotation, no runtime warning beyond a log line (which `DataInitializer` already had and this plan doesn't mention preserving), and no way to change it short of a code change and redeploy. An attacker with `/api/auth/login` access and this widely-known credential (visible in the plan doc itself, in `V2__seed_db.sql` history, and in this repo) gets full admin (or SUPERADMIN, see Finding 1) access.
- **Evidence:** `src/main/java/vn/springboot/config/DataInitializer.java:28-35` (current externalized defaults); `phase-02-java-seeder-framework-and-data-port.md:62` (hardcoded seed, no override mechanism mentioned); `plan.md:22` (`ddl-auto=update` in all profiles); `phase-02-java-seeder-framework-and-data-port.md:19` (non-dev seeds empty tables unconditionally, no "skip in production" gate).
- **Suggested fix:** Preserve `@Value`-based override for username/email/password in `UserSeeder` (env-var configurable per deployment), and add an explicit non-dev safeguard — e.g. refuse to seed the default admin password when `spring.profiles.active=production` unless an explicit override is supplied, or at minimum keep `DataInitializer`'s startup log warning ("change the default password!").

## Finding 3: Dev-mode full table reset (`userSeeder.reset()`) violates real FK constraints from unseeded domains, breaking the plan's own acceptance criterion

- **Severity:** Critical
- **Location:** Phase 2, section "Reset order" / `DomainSeeder.reset()` contract
- **Flaw:** `reset()` is specified as "delete all rows" (`phase-02...md:47`) and the dev-mode reset order ends with `... → userSeeder.reset() → shippingMethodSeeder.reset()` (`phase-02...md:66-70`). But `users` has real, `nullable=false` FK dependents that are explicitly *outside* the 13 seeded domains and never reset: `OrderEntity.user` (`OrderEntity.java:39-40`, `@JoinColumn(name="user_id", nullable=false)`, backed by `orders.user_id` FK per `V1__init_db.sql`), `CartItemEntity.user` (`CartItemEntity.java:38-39`, `nullable=false`), and `RefreshTokenEntity.user` (`RefreshTokenEntity.java:44-45`, `nullable=false`). None of `orders`, `cart_items`, `refresh_tokens` appear in the seeder's FK-safe/reset order lists (`phase-02...md:53-55, 66-70`) — they're intentionally out of scope for seeding, but `userSeeder.reset()` still tries to delete every row of `users`.
- **Failure scenario:** In any dev-mode session where a tester logs in (creates a `refresh_tokens` row), adds to cart, or places a test order — all completely normal manual QA activity per Phase 4's own verification steps ("Login check," "API sanity check") — the *next* server restart's `userSeeder.reset()` hits a live FK constraint violation deleting `users` while `orders`/`cart_items`/`refresh_tokens` rows still reference it. This directly breaks the plan's acceptance criterion "every restart against the same DB fully wipes and re-seeds all 13 domains" (`plan.md:47`) for the realistic case (not an edge case) of any interactive testing having happened since the last boot, and depending on how `SeedRunner` handles the exception, could abort seeding mid-reset, leaving all 12 already-reset domains empty while later ones (e.g. `shippingMethodSeeder`) still hold data — an inconsistent half-wiped DB.
- **Evidence:** `phase-02-java-seeder-framework-and-data-port.md:47` (`void reset(); // delete all rows`), `:66-70` (reset order, `users` and `shipping_methods` last, `orders`/`cart_items`/`refresh_tokens` absent), `V1__init_db.sql:245` (`orders` FK on `user_id`), `:184` (`cart_items` FK on `user_id`), `:300` (`refresh_tokens` FK on `user_id`); `src/main/java/vn/springboot/entity/order/OrderEntity.java:39-40`, `src/main/java/vn/springboot/entity/cart/CartItemEntity.java:38-39`, `src/main/java/vn/springboot/entity/user/RefreshTokenEntity.java:44-45` (all `optional=false`/`nullable=false`).
- **Suggested fix:** Either (a) scope `UserSeeder.reset()` to delete only the specific seeded admin row (`WHERE username='admin'`) instead of all users, or (b) explicitly cascade-reset `orders`/`cart_items`/`refresh_tokens` first (widening the "13 domains" scope and requiring the plan to own that decision), or (c) document that dev-mode reset is only safe on a DB with zero interactive-session activity since the last boot — which contradicts the plan's current unconditional framing.

## Finding 4: Hardcoded plaintext credentials + `ddl-auto=update` in production is a documented Hibernate anti-pattern with no compensating control in this plan

- **Severity:** High
- **Location:** Phase 3, "Requirements" / `application.yaml` change
- **Flaw:** `plan.md:22` and `phase-03...md:24,47` change `ddl-auto` from `validate` to `update` unconditionally, replacing the current explicit trust boundary where Hibernate only *validates* schema in every profile (`application.yaml:18-21`, comment: "Hibernate chỉ kiểm tra khớp, không tự sửa DB"). `update` lets Hibernate silently issue `ALTER TABLE`/`CREATE INDEX`/`CREATE TABLE` against the production schema on every boot based solely on whatever the entity classes currently say — with no review step, no migration file to diff in code review, and no rollback path. This is Hibernate's own documented anti-pattern for production (never additive-only in practice: a mistyped `@Column` or accidentally-loosened `nullable` on a merge conflict now mutates the live prod schema on next deploy instead of failing a `validate` check at boot).
- **Failure scenario:** A future PR that changes an entity annotation (e.g. drops `nullable=false`, changes a column length, or a bad merge reintroduces a stale field) silently alters the production schema shape on next deploy instead of the current fail-fast `validate` behavior, which would have blocked the deploy at boot with a clear Flyway/Hibernate mismatch error. This weakens a trust boundary that currently protects prod data integrity from unreviewed schema drift.
- **Evidence:** `application.yaml:18-21` (current `ddl-auto: validate` + comment establishing Hibernate-checks-only trust model); `plan.md:22` ("`ddl-auto=update` everywhere (dev + prod)"); `phase-03-remove-flyway-and-switch-to-code-first.md:24` (change to `update`); no mitigation for prod schema-drift risk anywhere in Phase 3/4 risk sections.
- **Suggested fix:** At minimum, note this as an accepted risk explicitly tied to "no real production data yet" (as `plan.md:22` already partially argues) with a documented follow-up to reintroduce migration-based (even code-first, e.g. Liquibase-generated-diff or Flyway-with-Hibernate-diff-tool) schema control before real production data/traffic exists — this isn't in the plan's acceptance criteria or Phase 4 docs list at all.

## Finding 5: Removing Flyway deletes the schema-change audit trail with no replacement, weakening incident forensics

- **Severity:** Medium
- **Location:** Phase 3, "Related Code Files" (deletes `db/migration/`, `db/seed/`)
- **Flaw:** Flyway's `flyway_schema_history` table (and the SQL files themselves) is the only record of *when* and *in what order* schema/data changes were applied to any given database instance. Phase 3 deletes the SQL files and stops running Flyway, and the risk section only notes the leftover `flyway_schema_history` table as "cosmetic" (`phase-03...md:54`) — it doesn't address that going forward there is zero mechanism (migration table, changelog, or otherwise) to reconstruct what schema state a given production DB is in, or when a given schema change landed, relative to `ddl-auto=update`'s silent, timestamp-less mutations.
- **Failure scenario:** During a future incident (e.g. investigating when/how a column's constraint changed, or reconciling schema drift between environments), there is no artifact to consult — `git log` on entity files is the only trail, and it doesn't tell you which commit was actually deployed against which live database at the time of an incident.
- **Evidence:** `phase-03-remove-flyway-and-switch-to-code-first.md:27-28` (delete `db/migration/`, `db/seed/` entirely), `:54` (dismisses `flyway_schema_history` as merely "cosmetic" without addressing the forward-looking audit gap).
- **Suggested fix:** Explicitly document this tradeoff in Phase 4's docs (system-architecture.md) as an accepted limitation, or keep `git log` on entity files as the stated substitute so it's a conscious decision, not a silent gap.

## Finding 6: `SeedRunner`'s destructive dev-mode reset has a single-flag trigger with no confirmation gate, and Phase 2 skips verifying it against pre-existing FK data

- **Severity:** High
- **Location:** Phase 2, "Implementation Steps" step 11 (manual verification)
- **Flaw:** The manual verification step ("start with `APP_ENV=development`, confirm all 13 domains got seeded... restart, confirm full reset+reseed happened again cleanly") only tests reset on a DB whose *only* state is the seeder's own 13 domains — it never tests the realistic scenario from Finding 3 (a logged-in session, a cart item, an order existing before restart). A single environment variable (`APP_ENV=development`) is the only gate on an operation that unconditionally deletes all rows in 12+ tables, same single-point-of-failure risk as the current Flyway `clean()` behavior it replaces, but now happening on *every* restart instead of only on a checksum-mismatch — increasing the frequency this destructive path executes in any shared/long-lived "development"-tagged environment.
- **Failure scenario:** Same blast radius as Finding 3 plus: if `APP_ENV=development` is ever set against a shared staging DB with real accumulated test data (common in small teams that don't have a fully separate throwaway DB per developer), every single restart destroys that data, not just checksum-mismatch restarts as today.
- **Evidence:** `phase-02-java-seeder-framework-and-data-port.md:85` (verification step never includes a pre-existing order/cart/session scenario); `.env.example:5-7` (current comment already flags dev DB as "disposable" but ties destruction to migration/seed *changes*, not every boot).
- **Suggested fix:** Add the FK-dependent-data scenario to Phase 2 step 11's manual verification explicitly (this would have caught Finding 3), and consider requiring a second explicit flag (e.g. `SEED_RESET_CONFIRM=true`) alongside `APP_ENV=development` before wiping data on every boot, rather than reusing the profile flag alone for a much higher-frequency destructive trigger.

## Finding 7 (Fact-check): Plan misattributes `DataInitializer`'s default admin email as `admin@gmail.com`

- **Severity:** Medium
- **Location:** `plan.md:26` ("retire `DataInitializer.java`'s losing `admin@gmail.com` default")
- **Flaw:** `DataInitializer.java:31` shows the actual default is `@Value("${app.init.admin-email:admin@springboot.vn}")` — `admin@springboot.vn`, not `admin@gmail.com`. The `admin@gmail.com` value only appears in `README.md:158` as stale documentation, not in `DataInitializer.java` itself. The plan conflates "README's stale claim" with "DataInitializer's actual default," which is a fact-check failure on a security-adjacent detail (which admin identity/domain is actually in play matters when reasoning about credential exposure).
- **Evidence:** VERIFIED (`README.md:158`, `admin@gmail.com`) vs FAILED (`DataInitializer.java:31`, actual default is `admin@springboot.vn`, not `admin@gmail.com`).
- **Suggested fix:** Correct the plan's phrasing to distinguish "README's stale/wrong claim (`admin@gmail.com`)" from "DataInitializer's actual default (`admin@springboot.vn`), which is a third, different, dead-code identity that also needs to disappear" — three distinct admin identities exist across the codebase pre-migration (SQL seed: `admin@gomvugia.vn`/ADMIN; `DataInitializer` default: `admin@springboot.vn`/SUPERADMIN; README doc: `admin@gmail.com`), not two, and the plan should acknowledge all three when claiming consolidation to "the" canonical identity.
